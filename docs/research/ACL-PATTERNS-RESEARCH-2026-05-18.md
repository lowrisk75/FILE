## Executive Summary

This research examines access control and ACL patterns across industry standards (TURN/STUN RFCs), production implementations (Tailscale DERP, Coturn, LibP2P), security frameworks (Zero Trust, SOC 2), and compliance requirements (GDPR). Key findings:

1. **Authentication Layering**: Most successful relay systems use multiple authentication layers (network → transport → application), not a single gate.

2. **Zero Trust Foundation**: Modern relay architectures (Tailscale, Signal) favor cryptographic peer authentication over traditional username/password systems.

3. **Minimal Trust Surface**: The "dumb pipe" design in FILE's current ACCESS-CONTROL.md aligns with industry best practices—keep relays stateless and cryptographically blind.

4. **Compliance Trade-offs**: GDPR and SOC 2 requirements conflict with operational needs—IP logging is necessary for abuse prevention but requires careful handling (hashing, retention limits, purpose limitation).

5. **Rate Limiting is Critical**: Every production relay system implements multi-dimensional rate limiting (per-IP, per-user, per-resource) as the primary DoS defense.

**Recommendation**: FILE's current 5-level ACL design (Admin → Network → Registration → P2P → Application) is architecturally sound. Implement Level 1 (admin ACLs) immediately, Level 3 (API keys) for managed deployments, and defer Level 4 (P2P ACLs) unless spam becomes a proven problem.

## 1. Industry Standards: TURN/STUN Server ACLs (RFC 5766 & RFC 8656)

### Overview

TURN (Traversal Using Relays around NAT) is the closest standardized protocol to FILE's relay architecture. RFC 5766 (2010) and its successor RFC 8656 (2020) define authentication and access control mechanisms for WebRTC relay servers.

### Key Authentication Mechanisms

#### 1.1 Long-Term Credentials (LTC)

**Specification**: RFC 5766 Section 10  
**Mechanism**: STUN long-term credential mechanism with MESSAGE-INTEGRITY attribute

- Client authenticates using username + password (sent via STUN attributes)
- Server validates credentials using HMAC-SHA1 (RFC 5766) or SHA-256 (RFC 8656)
- Credentials persist for the duration of the session (typically 5-10 minutes)

**Security Properties**:
- ✅ Prevents unauthorized relay usage
- ✅ Allows per-user quotas and billing
- ❌ Vulnerable to credential theft (requires HTTPS/TLS distribution)
- ❌ Requires credential database (PostgreSQL, Redis, etc.)

**Implementation Example (Coturn)**:
```bash
# Static user database
user=alice:password123:realm

# Or dynamic via PostgreSQL
psql-userdb="host=localhost dbname=turn user=turn password=secret"
```

#### 1.2 Short-Term Credentials (REST API)

**Specification**: Draft-uberti-behave-turn-rest-00  
**Mechanism**: Time-limited tokens generated by application backend

1. Client requests token from application server (HTTPS)
2. Server generates `username = timestamp:hmac(timestamp, secret)`
3. Client uses token with TURN server
4. TURN server validates HMAC and expiration

**Security Properties**:
- ✅ No credential storage on TURN server (stateless)
- ✅ Automatic expiration (typically 24 hours)
- ✅ Prevents credential reuse attacks
- ✅ Scales horizontally (no shared state)

**Coturn Configuration**:
```bash
use-auth-secret
static-auth-secret=MySecretKey123
```

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
This is the **recommended approach** for FILE's Level 3 (Registration ACLs). Generate time-limited tokens server-side, validate HMAC client-side. No database required.

#### 1.3 OAuth 2.0 (RFC 7635)

**Specification**: RFC 7635 - Session Traversal Utilities for NAT (STUN) Extension for Third-Party Authorization

- Client obtains OAuth 2.0 access token from authorization server
- TURN server validates token with authorization server (or via JWT signature)
- Supports fine-grained scopes (e.g., "turn:relay", "turn:allocate")

**Security Properties**:
- ✅ Industry-standard authorization flow
- ✅ Centralized policy management
- ✅ Token revocation support
- ❌ Requires OAuth infrastructure (authorization server, token validation)
- ❌ Higher latency (token validation roundtrip)

**FILE Relay Applicability**: ⭐⭐  
Overkill for FILE's use case. OAuth adds complexity (authorization server dependency) without clear benefits over time-limited HMAC tokens.

### 1.4 Permissions System (RFC 5766 Section 9)

**Problem**: Enterprise IT administrators fear TURN could bypass corporate firewalls.

**Solution**: TURN includes a **permissions system** where clients must explicitly install permissions before relaying to a peer.

**Mechanism**:
1. Client sends `CreatePermission(peer_ip_address)` request
2. Server installs permission (valid for 5 minutes)
3. Client can now relay packets to/from that peer IP
4. Permission expires automatically (cannot be explicitly deleted)

**Example Flow**:
```
Client → TURN: CreatePermission(192.0.2.50)
TURN → Client: Success
Client → TURN: Send(data, 192.0.2.50)  ✅ Allowed
Client → TURN: Send(data, 198.51.100.10)  ❌ Blocked (no permission)
```

**Security Properties**:
- ✅ Prevents relay as open proxy (attacker cannot relay to arbitrary IPs)
- ✅ Automatic expiration limits abuse window
- ❌ Doesn't prevent spam between permitted peers
- ❌ Adds latency (must install permission before first packet)

**FILE Relay Applicability**: ⭐⭐⭐  
Relevant for FILE's Level 4 (P2P ACLs). However, FILE uses peer_ids (not IP addresses), so permissions would be per-peer_id. Consider implementing if spam becomes a problem.

### 1.5 Transport-Layer Security (RFC 8656 Section 5)

**Requirement**: RFC 8656 mandates support for DTLS-over-UDP and TLS-over-TCP between client and TURN server.

**Rationale**:
- TURN's digest authentication doesn't protect against passive eavesdropping
- TLS provides server authentication (client knows it's talking to the correct server)
- TLS encrypts TURN control messages (prevents metadata leaks)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
**Critical**. FILE's current design has no transport security (SEC-C06 finding). Implement Noise XX handshake before registration to provide mutual authentication + confidentiality.

## 2. Tailscale DERP: Zero-Trust Relay Architecture

### 2.1 Overview

Tailscale DERP (Designated Encrypted Relay for Packets) is the closest production analog to FILE's relay design:
- Frame-based protocol over HTTP/WebSocket
- Relays encrypted WireGuard packets between peers
- Zero knowledge architecture (relay cannot decrypt traffic)
- Mesh relay topology for redundancy

### 2.2 Authentication Model

#### Client Authentication

**Mechanism**: Clients authenticate via the **control plane** (coordination server), not directly with DERP servers.

**Flow**:
1. Client authenticates with Tailscale coordination server (SSO, OAuth, SAML)
2. Coordination server issues a **Tailscale key** (Ed25519 public key = peer identity)
3. Client connects to DERP server and presents key
4. DERP validates key against coordination server OR uses pre-shared mesh key

**Key Insight**: DERP servers don't maintain user accounts—they trust the coordination plane's authentication decision.

**FILE Relay Applicability**: ⭐⭐⭐⭐  
This is the **architecture FILE should adopt**:
- Relay trusts a separate authentication service (could be a simple JWT-issuing backend)
- Relay validates peer_id signatures, not passwords
- Decouples identity management from relay operations

#### Custom DERP Verification

For self-hosted DERP servers, Tailscale supports `DERP_VERIFY_CLIENTS=true`:
- DERP queries the local tailscaled daemon to verify client public keys
- Prevents "freeloaders" from using your relay without authorization
- Requires DERP server to have access to tailscaled control socket

**FILE Relay Applicability**: ⭐⭐⭐  
For private FILE deployments, implement a simple webhook: relay calls `POST /verify-peer` with peer_id, backend returns 200 (allowed) or 403 (denied).

### 2.3 Mesh Authentication

**Problem**: DERP servers in a region need to forward packets to each other.

**Solution**: Pre-shared key (PSK) authentication between DERP servers.

**Mechanism**:
- Each DERP server configured with same `mesh-psk`
- Servers authenticate via PSK before forwarding packets
- Prevents rogue servers from joining mesh

**FILE Relay Applicability**: ⭐⭐⭐⭐  
Highly relevant for FILE's multi-relay architecture. Implement PSK-based mesh authentication before deploying 3-relay production topology.

### 2.4 Capability-Based ACLs

Tailscale's control plane supports **capability-based matching**:
- ACLs based on node capabilities, not just IP addresses
- Example: "Allow nodes with capability:admin to access nodes with tag:server"
- Fine-grained, dynamic access control

**FILE Relay Applicability**: ⭐⭐  
Overkill for relay layer—this belongs in FILE's application layer (Level 5 ACLs). Clients should implement capability checks, not relays.

### 2.5 Encryption Model

**Critical Design Choice**: Tailscale encrypts **all data** end-to-end with WireGuard, even through DERP.

**Implication**: DERP servers see:
- ✅ Source/destination public keys (routing)
- ✅ Packet sizes and timing (metadata)
- ❌ **Packet contents** (encrypted with WireGuard)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE already implements this with Noise protocol + AONT fragmentation. This is the **correct security model** for zero-trust relays.

### 2.6 Key Takeaways

1. **Separate authentication from relay**: Use a control plane (coordination server) for identity management. Relays validate tokens/keys, not passwords.

2. **Public key = identity**: Peer public keys serve as addresses. No usernames, no sessions, no database lookups.

3. **Zero knowledge by design**: Relay must not be able to decrypt traffic. This is a security feature, not a limitation.

4. **Mesh requires authentication**: If deploying multiple relays, implement mesh PSK authentication to prevent rogue servers.

## 3. WebRTC TURN Security Best Practices

### 3.1 Authentication Requirements

**Industry Consensus** (from VideoSDK, Ant Media, WebRTC.ventures):

1. **Never run an open relay**: Always require authentication (long-term credentials or REST API tokens).

2. **Use time-limited credentials**: REST API credentials expire after 24 hours, limiting credential theft impact.

3. **Strong password hashing**: SHA-256 minimum (SHA-1 deprecated in RFC 8656).

4. **Restrict IP ranges** (optional): Enterprise deployments whitelist corporate IP ranges in firewall.

### 3.2 Monitoring and Anomaly Detection

**Critical Metrics** (from WebRTC Security guides):

- **Authentication failure rate**: Alert if >5% of TURN requests fail authentication
- **Allocation spikes**: Alert on sudden increase in relay allocations (possible DoS)
- **Unusual geolocation**: Flag connections from unexpected countries
- **Bandwidth per user**: Alert if single user exceeds quota (e.g., >10 GB/day)

**Implementation**:
- Prometheus metrics + Grafana dashboards
- PagerDuty/Slack alerts for anomalies
- Fail2ban for automatic IP blocking (>10 failed auth attempts)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
**Mandatory**. FILE already has Prometheus metrics (AtomicU64 counters). Add:
- `relay_auth_failures_total` (counter)
- `relay_bandwidth_bytes_per_peer` (histogram)
- `relay_connections_by_country` (gauge, from GeoIP)

### 3.3 Access Control Best Practices

**From WebRTC security guides**:

1. **OAuth tokens over static passwords**: OAuth 2.0 provides fine-grained scopes and token revocation.

2. **Least privilege**: Grant only necessary permissions (e.g., "relay:send" vs "relay:admin").

3. **Audit logs**: Log all authentication attempts (success + failure) for incident response.

4. **Rate limiting**: Implement per-IP and per-user rate limits to prevent abuse.

**FILE Relay Applicability**:
- ⭐⭐⭐⭐⭐ Rate limiting (already in ACCESS-CONTROL.md Phase 1)
- ⭐⭐⭐⭐⭐ Audit logs (add structured logging for auth events)
- ⭐⭐⭐ OAuth (overkill—use HMAC tokens instead)
- ⭐⭐⭐ Least privilege (implement via token scopes if using API keys)

## 4. LibP2P Peer Authentication Patterns

### 4.1 Peer ID as Identity

**Core Principle**: Every LibP2P peer is uniquely identified by their **Peer ID**, derived from a cryptographic public key.

**Advantages**:
- ✅ Self-authenticating (Peer ID = hash of public key)
- ✅ No central authority (peer generates identity locally)
- ✅ Decentralized trust (peers verify signatures, not certificates)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE already uses peer_ids (Ed25519 public keys). This is the **correct design**. Peer IDs serve as routing addresses and authentication tokens.

### 4.2 Secure Communication Protocols

#### TLS 1.3 (libp2p-tls)

**Mechanism**: Encode public key into TLS certificate. Peer derives Peer ID from certificate and verifies it matches expected ID.

**Security Properties**:
- ✅ Standard TLS security properties (confidentiality, integrity, authentication)
- ✅ Resistant to downgrade attacks
- ❌ Relies on X.509 PKI (complexity)

#### Noise Protocol (libp2p-noise)

**Mechanism**: Noise XX handshake pattern provides mutual authentication of static keys.

**Security Properties**:
- ✅ Forward secrecy + post-compromise security
- ✅ Replay attack resistance
- ✅ Simpler than TLS (no X.509 certificates)
- ✅ Handshake payload encryption (metadata protection)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE uses Noise XX for client-relay authentication (SEC-C06 remediation). This is the **industry-standard choice** for P2P systems.

### 4.3 Authorization Model

**Key Insight**: LibP2P provides **authentication** (proving peer identity) but **NOT authorization** (deciding what peers can do).

**From LibP2P docs**:
> "libp2p does not provide an authorization framework 'out of the box' since requirements vary widely across peer-to-peer systems."

**Recommendation**:
- Authenticate peer_ids at the transport layer (Noise protocol)
- Implement authorization at the application layer (client-side filtering)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
This is **exactly FILE's design**. Relay authenticates peer_ids (Level 3), but clients decide which peers to accept messages from (Level 5). Relay does NOT enforce P2P ACLs (Level 4) by default.

### 4.4 Zero-Trust Architecture

**LibP2P Security Considerations**:
- Assume all inputs are malicious (validate packet formats, sizes, rates)
- Use authenticated encryption (AES-GCM, ChaCha20-Poly1305)
- Implement replay protection (nonce tracking)
- Rate-limit all operations (connection attempts, message sends)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE's SYSTEM-OVERVIEW.md already describes a zero-trust relay:
- CAPoW proof-of-work (DoS resistance)
- Per-IP rate limiting
- Replay cache for CAPoW proofs
- Packet validation (peer_id format, size limits)

## 5. WireGuard: Key-Based Authentication Model

### 5.1 Authentication Mechanism

**Core Principle**: WireGuard peers authenticate via **pre-shared public keys**, not certificates or passwords.

**Mechanism**:
1. Each peer has a Curve25519 key pair
2. Peers configure each other's public keys out-of-band (manual or via control plane)
3. NoiseIK handshake provides mutual authentication + key exchange

**Security Properties**:
- ✅ Zero-knowledge (no user accounts, no identity provider)
- ✅ Forward secrecy + post-compromise security
- ✅ Extremely simple (no PKI, no certificates, no OCSP)
- ❌ Key distribution is manual (requires control plane for automation)

**FILE Relay Applicability**: ⭐⭐⭐⭐  
FILE uses Ed25519 peer_ids similarly to WireGuard's public keys. The key difference: FILE relays must route packets between ANY peers (not just pre-configured peers), so relays cannot validate peer relationships.

### 5.2 Cryptographic Simplicity

**WireGuard's Philosophy**: Restrict cryptographic options to a small, audited set:
- Curve25519 (ECDH)
- ChaCha20-Poly1305 (AEAD)
- BLAKE2s (hashing)
- HKDF (key derivation)

**Implication**: No cipher negotiation, no downgrade attacks, no weak crypto.

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE's crypto_fabric already follows this principle:
- Ed25519 (signatures)
- ML-KEM-768 (post-quantum key encapsulation)
- Noise XX (authenticated encryption)
- AONT (all-or-nothing transform)

**Recommendation**: Resist adding cipher negotiation or optional crypto. Keep the stack simple and auditable.

### 5.3 Pre-Shared Key (PSK) Mode

**Purpose**: Add symmetric key layer to mitigate quantum computing threats.

**Mechanism**: Both peers share a symmetric key (out-of-band). During handshake, PSK is mixed into key derivation.

**Security Properties**:
- ✅ Post-quantum security (symmetric crypto is quantum-resistant)
- ✅ Additional layer even if ECC is broken
- ❌ Key distribution complexity (must securely share PSK)

**FILE Relay Applicability**: ⭐⭐⭐  
FILE already has ML-KEM-768 (post-quantum KEM), so PSK is less critical. However, consider PSK for **relay mesh authentication** (relays share a PSK to prevent rogue servers).

## 6. Signal Private Messenger: Relay Security Model

### 6.1 End-to-End Encryption

**Core Principle**: Signal servers **relay** messages but cannot decrypt them.

**Mechanism**:
- Signal Protocol (Double Ratchet) provides E2EE
- Servers route messages by recipient identifier (phone number or UUID)
- Servers cannot access message contents, attachments, or metadata (beyond timing/volume)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
This is **FILE's exact model**:
- Relay routes packets by peer_id
- Noise + AONT ensure relay cannot decrypt contents
- Relay sees metadata (IP addresses, timing, packet sizes) but not data

### 6.2 Metadata Protection (Sealed Sender)

**Problem**: Signal servers know who sends messages to whom (social graph metadata).

**Solution**: **Sealed Sender** hides sender identity from server.

**Mechanism**:
1. Sender encrypts message with recipient's public key
2. Sender encrypts *sender identity* with recipient's public key (nested encryption)
3. Server only sees recipient address, not sender
4. Recipient decrypts message to reveal sender

**Limitation**: Server still sees recipient address and timing.

**FILE Relay Applicability**: ⭐⭐⭐  
Relevant for FILE's privacy model. Consider implementing "sealed relay packets":
- Client encrypts peer_id with relay's public key (ephemeral session key)
- Relay decrypts to get dest_peer_id, but source_peer_id remains encrypted
- Destination peer decrypts to reveal source

**Trade-off**: Adds complexity + latency. Only implement if metadata privacy is a core requirement.

### 6.3 Forward Secrecy and Post-Compromise Security

**Signal Protocol Properties**:
- **Forward secrecy**: Past messages safe if current key compromised
- **Post-compromise security**: Future messages safe after key recovery

**Mechanism**: Double Ratchet algorithm continuously derives new keys.

**FILE Relay Applicability**: ⭐⭐⭐⭐  
FILE's Noise XX handshake provides forward secrecy. For long-lived relay connections, consider **key rotation**:
- Rotate Noise session keys every N minutes (e.g., 10 minutes)
- Requires re-handshake, but limits key compromise window

### 6.4 Open Source Transparency

**Signal's Approach**: All client and server code is open source (GitHub).

**Rationale**: Security through transparency—adversaries can audit code, but cannot find backdoors because there are none.

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE is already open source. Ensure all crypto code is well-documented and invite external audits.

## 7. Zero Trust Relay Architectures

### 7.1 Core Principles

**Zero Trust Model** (from 2026 guides):

1. **Never trust, always verify**: Every request is authenticated and authorized, regardless of source.

2. **Least privilege access**: Grant minimum necessary permissions for specific tasks.

3. **Assume breach**: Design systems to contain and detect compromises, not prevent them entirely.

4. **Continuous validation**: Authentication is not a one-time event—validate on every request.

5. **Microsegmentation**: Isolate workloads to limit lateral movement.

### 7.2 Authentication and Authorization Patterns

**Modern Zero Trust Approach**:
- Multi-factor authentication (MFA) beyond passwords
- Dynamic risk assessment (device posture, geolocation, behavior)
- Just-in-time access (temporary permissions, auto-revoked)
- Microsegmentation (network isolation per tenant/workload)

**FILE Relay Applicability**:
- ⭐⭐⭐⭐⭐ Always verify (CAPoW + Noise authentication on every connection)
- ⭐⭐⭐⭐ Assume breach (AONT fragmentation limits single relay compromise)
- ⭐⭐⭐ Continuous validation (re-authenticate on session expiry)
- ⭐⭐ Microsegmentation (relevant for multi-tenant deployments)

### 7.3 Stateless Authentication

**Problem**: Stateful authentication (sessions, databases) creates bottlenecks and single points of failure.

**Solution**: **Stateless authentication** via JWTs or signed tokens.

**Mechanism**:
1. Client authenticates with identity provider
2. Identity provider issues JWT (signed with private key)
3. Client presents JWT to relay
4. Relay validates JWT signature (no database lookup)

**Advantages**:
- ✅ Horizontal scalability (no shared state)
- ✅ Fast (signature verification < 1ms)
- ✅ No database dependency

**Disadvantages**:
- ❌ Cannot revoke tokens before expiry (must wait for timeout)
- ❌ Token theft risk (mitigated by short expiry + HTTPS)

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
**Highly recommended**. Implement Level 3 (Registration ACLs) using JWT-like tokens:
- Token = `timestamp || HMAC(peer_id || timestamp, secret)`
- Relay validates HMAC and expiry (no database)
- Tokens expire after 24 hours (client re-authenticates with backend)

## 8. DDoS Mitigation and Rate Limiting

### 8.1 Multi-Dimensional Rate Limiting

**Industry Best Practice**: Implement rate limits at multiple levels.

#### Per-IP Rate Limiting

**Purpose**: Prevent single attacker IP from exhausting relay resources.

**Typical Limits**:
- Registration: 10 requests/sec sustained, 50 burst
- Packet forwarding: 1000 packets/sec sustained, 5000 burst

**Implementation** (from FILE ACCESS-CONTROL.md):
```rust
struct RateLimiter {
    per_ip: DashMap<IpAddr, TokenBucket>,
}

impl RateLimiter {
    async fn check(&self, ip: IpAddr) -> Result<(), Error> {
        let bucket = self.per_ip.entry(ip).or_insert_with(|| {
            TokenBucket::new(10.0, 50)  // 10/s sustained, 50 burst
        });
        
        bucket.consume(1).await?;
        Ok(())
    }
}
```

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
Already in ACCESS-CONTROL.md. **Implement immediately** (SEC-C03 critical finding).

#### Per-User Rate Limiting

**Purpose**: Prevent single user (multiple IPs via botnet) from exhausting relay.

**Typical Limits**:
- Max 10 peers per user
- Max 1 GB/day bandwidth per user

**Implementation**:
```rust
struct UserQuota {
    user_id: UserId,
    max_peers: usize,
    current_peers: AtomicUsize,
    bandwidth_used: AtomicU64,  // bytes today
    reset_at: Instant,           // daily reset
}
```

**FILE Relay Applicability**: ⭐⭐⭐⭐  
Relevant for Level 3 (API key authentication). If implementing API keys, add per-user quotas.

#### Per-Resource Rate Limiting

**Purpose**: Protect specific resources (e.g., CAPoW verification is CPU-expensive).

**Typical Limits**:
- CAPoW verification: 100/sec globally (even if from different IPs)
- Peer registry updates: 1000/sec globally

**Implementation**:
```rust
struct GlobalRateLimiter {
    capow_verifications: AtomicU64,
    window_start: AtomicInstant,
}

impl GlobalRateLimiter {
    fn check_capow(&self) -> Result<(), Error> {
        let now = Instant::now();
        let count = self.capow_verifications.fetch_add(1, Ordering::Relaxed);
        
        if count > 100 && now - self.window_start.load() < Duration::from_secs(1) {
            return Err(Error::GlobalRateLimitExceeded);
        }
        
        Ok(())
    }
}
```

**FILE Relay Applicability**: ⭐⭐⭐⭐  
Relevant if CAPoW verification becomes a bottleneck. Monitor `capow_verification_duration_seconds` histogram and add global limit if P99 latency > 100ms.

### 8.2 Proof-of-Work (CAPoW)

**FILE's Approach**: CAPoW (Computational Amortized Proof-of-Work) requires clients to solve Argon2 puzzle before registration.

**Security Properties**:
- ✅ DoS resistance (attackers must spend CPU time)
- ✅ Fair (legitimate clients pay small cost, attackers pay large aggregate cost)
- ✅ Adaptive difficulty (relay can increase difficulty under load)

**Industry Comparison**:
- **Cloudflare Turnstile**: PoW challenges for bot detection
- **Hashcash**: Email spam prevention (defunct, but pioneered PoW)
- **Bitcoin**: PoW for Sybil resistance

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
CAPoW is **critical** (SEC-C01 finding: currently disabled). **Implement immediately**.

### 8.3 Adaptive Rate Limiting

**Concept**: Adjust rate limits dynamically based on server load.

**Example**:
- Normal load: 10 registrations/sec per IP
- High load (CPU >80%): 5 registrations/sec per IP
- Critical load (CPU >95%): 1 registration/sec per IP

**Implementation**:
```rust
fn get_rate_limit(&self) -> f64 {
    let cpu_usage = self.metrics.cpu_usage.load(Ordering::Relaxed);
    
    match cpu_usage {
        0..=80 => 10.0,      // normal
        81..=95 => 5.0,      // high load
        _ => 1.0,            // critical load
    }
}
```

**FILE Relay Applicability**: ⭐⭐⭐  
Nice-to-have, not critical. Implement after basic rate limiting is stable.

## 9. Multi-Tenancy Isolation

### 9.1 Tenant ID in Identifier

**Approach**: Encode tenant ID into peer_id or relay address.

**Example**:
```
peer_id = tenant_id (16 bytes) || random (16 bytes)
```

**Relay Enforcement**:
```rust
fn validate_relay(src: PeerId, dest: PeerId) -> Result<(), Error> {
    let src_tenant = extract_tenant_id(src);
    let dest_tenant = extract_tenant_id(dest);
    
    if src_tenant != dest_tenant {
        return Err(Error::CrossTenantNotAllowed);
    }
    
    Ok(())
}
```

**Advantages**:
- ✅ Simple (no external state)
- ✅ Fast (tenant ID in packet)
- ✅ Stateless (relay doesn't need tenant database)

**Disadvantages**:
- ❌ Reduces peer_id entropy (16 bytes instead of 32)
- ❌ Tenant ID visible in packets (privacy concern)
- ❌ Cannot change tenant (peer_id is immutable)

**FILE Relay Applicability**: ⭐⭐⭐  
Viable for lightweight multi-tenancy. Use if deploying a single relay instance for multiple small organizations.

### 9.2 Tenant-Specific Relay Instances

**Approach**: Deploy separate relay instance per tenant.

**Kubernetes Example**:
```yaml
# Namespace per tenant
apiVersion: v1
kind: Namespace
metadata:
  name: tenant-acme

---
# Deployment per tenant
apiVersion: apps/v1
kind: Deployment
metadata:
  name: file-relay
  namespace: tenant-acme
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: relay
          image: file-relay:latest
          env:
            - name: TENANT_ID
              value: "acme"
```

**Advantages**:
- ✅ Strong isolation (separate processes, namespaces, networks)
- ✅ Tenant-specific configs (rate limits, quotas, logging)
- ✅ Easy to scale per tenant
- ✅ Blast radius containment (one tenant's DoS doesn't affect others)

**Disadvantages**:
- ❌ Higher infrastructure cost (more pods/VMs)
- ❌ More complex to manage (multiple deployments)

**FILE Relay Applicability**: ⭐⭐⭐⭐  
**Recommended for enterprise/B2B deployments**. Strong isolation justifies cost for paying customers.

### 9.3 VLAN/Network Namespace Isolation

**Approach**: Use kernel network namespaces + VLANs to isolate tenants.

**Mechanism** (from multi-tenant relay research):
- Each tenant gets a Linux network namespace
- Each namespace has a VLAN ID
- Relay routes packets only within tenant's VLAN

**Advantages**:
- ✅ Strong isolation (kernel-enforced)
- ✅ Single relay process (lower overhead than separate VMs)
- ✅ Supports IP address overlap across tenants

**Disadvantages**:
- ❌ Complex setup (requires network engineering)
- ❌ Linux-specific (not portable to Windows/macOS)
- ❌ Harder to debug (network namespace isolation)

**FILE Relay Applicability**: ⭐⭐  
Overkill for most FILE deployments. Only relevant for large-scale SaaS with 100+ tenants.

### 9.4 Recommendation

**For FILE**:
- **Small deployments (1-10 orgs)**: Use Tenant ID in peer_id (Option 9.1)
- **Enterprise/B2B (10-100 orgs)**: Use separate relay instances per tenant (Option 9.2)
- **Large-scale SaaS (100+ orgs)**: Consider VLAN/namespace isolation (Option 9.3) OR horizontal sharding (multiple relay clusters)

## 10. GDPR Compliance for Relay Logging

### 10.1 IP Addresses as Personal Data

**GDPR Interpretation**: IP addresses are **personal data** under GDPR Article 4(1).

**Rationale**: IP addresses can identify individuals (especially static IPs or combined with ISP logs).

**Implication**: Logging IP addresses requires:
1. **Legal basis** (e.g., legitimate interest in preventing abuse)
2. **Purpose limitation** (only use for stated purpose)
3. **Transparency** (inform users in privacy policy)
4. **Storage limitation** (delete logs after retention period)

### 10.2 Anonymization vs Pseudonymization

**Anonymization**: Irreversibly remove identifiers (GDPR no longer applies).

**Example**: Hash IP addresses with HMAC:
```rust
fn hash_ip(ip: IpAddr, secret: &[u8]) -> [u8; 32] {
    let mut mac = Hmac::<Sha256>::new_from_slice(secret).unwrap();
    mac.update(&ip.to_string().as_bytes());
    mac.finalize().into_bytes().into()
}
```

**Pseudonymization**: Replace identifiers with pseudonyms (GDPR still applies, but lower risk).

**Example**: Truncate IP addresses:
```
Full IP: 192.0.2.123
Truncated: 192.0.2.0 (last octet removed)
```

**GDPR Preference**: Anonymization is better (GDPR exemption), but pseudonymization is acceptable with safeguards.

**FILE Relay Applicability**: ⭐⭐⭐⭐⭐  
FILE's ACCESS-CONTROL.md specifies HMAC-SHA256 hashing (anonymization). **This is correct**. Implement immediately (SEC-C04 critical finding).

### 10.3 Data Retention Limits

**GDPR Principle**: Retain personal data only as long as necessary for the stated purpose.

**Typical Retention Periods**:
- **Operational logs**: 7-30 days (troubleshooting, performance monitoring)
- **Security logs**: 90 days (incident response, forensics)
- **Audit logs**: 1-7 years (compliance, legal hold)

**FILE Relay Recommendation**:
- Peer registry (in-memory): TTL = 10 minutes (heartbeat timeout)
- Rate limiter state: TTL = 1 minute (sliding window)
- Metrics (Prometheus): 30 days retention
- Structured logs (if persistent): 7 days for operational, 90 days for security

### 10.4 User Rights (GDPR Articles 15-22)

**Right to Access** (Article 15): Users can request all data you hold about them.

**Right to Erasure** (Article 17): Users can request deletion ("right to be forgotten").

**Right to Rectification** (Article 16): Users can request corrections.

**FILE Relay Implication**: If relay logs are **truly anonymized** (HMAC-hashed IPs), these rights don't apply (cannot identify the user). If pseudonymized, must support data subject requests.

### 10.5 Lawful Basis for Processing

**GDPR Article 6** requires a lawful basis for processing personal data.

**Relevant Bases for Relay Logs**:
1. **Legitimate Interest** (Article 6(1)(f)): Preventing abuse, ensuring security
2. **Contract** (Article 6(1)(b)): Necessary to provide relay service
3. **Consent** (Article 6(1)(a)): User explicitly consents (requires opt-in)

**FILE Relay Recommendation**: Use **Legitimate Interest** for IP logging (abuse prevention). Document in privacy policy: "We log hashed IP addresses to prevent abuse and ensure service availability."

### 10.6 Peer IDs and GDPR

**Question**: Are peer_ids (Ed25519 public keys) personal data?

**Analysis**:
- Peer IDs are generated locally by clients (not assigned by relay)
- Peer IDs are pseudonymous (not directly identifiable)
- However, combined with metadata (IP, timing), peer IDs **could** identify users

**GDPR Classification**: **Pseudonymous data** (GDPR applies).

**Implication**: Treat peer_ids as personal data. Apply same retention limits and user rights.

**FILE Relay Approach**:
- Don't log peer_ids in plaintext (hash them like IPs)
- Include peer_ids in privacy policy ("unique device identifiers")
- Support deletion (allow users to deregister peer_id)

## 11. SOC 2 Access Control Requirements

### 11.1 Overview

**SOC 2** (Service Organization Control 2) is an auditing framework for cloud/SaaS providers.

**Trust Service Criteria**:
1. **Security** (mandatory)
2. Availability (optional)
3. Confidentiality (optional)
4. Processing Integrity (optional)
5. Privacy (optional)

**FILE Relay Focus**: **Security** is most relevant for relay infrastructure.

### 11.2 Common Criteria (CC) for Access Control

#### CC6.1: Logical and Physical Access Controls

**Requirement**: Restrict logical and physical access to authorized users.

**Evidence Required**:
- Network firewall rules (who can access relay port 8080?)
- SSH access logs (who can access relay VMs?)
- IAM policies (who can modify relay configs?)

**FILE Relay Implementation**:
- **Network ACLs**: Port 8080 open to 0.0.0.0/0 (public relay), OR restricted to VPN (private relay)
- **Admin access**: SSH keys only (no passwords), MFA for cloud console
- **Metrics endpoint**: Port 8081 restricted to monitoring network (Prometheus)

#### CC6.2: Authentication

**Requirement**: Authenticate users before granting access.

**Evidence Required**:
- Relay authentication mechanism (CAPoW + Noise handshake)
- Admin authentication logs (SSH key fingerprints, MFA events)
- Failed authentication attempts (brute force detection)

**FILE Relay Implementation**:
- CAPoW proof-of-work (prevent anonymous abuse)
- Noise XX handshake (mutual authentication of peers)
- Admin SSH with publickey only (`PasswordAuthentication no`)

#### CC6.3: Authorization

**Requirement**: Grant minimum necessary access (least privilege).

**Evidence Required**:
- Role-based access control (RBAC) policies
- Privilege escalation logs (sudo, admin actions)
- Periodic access reviews (quarterly audit of who has access)

**FILE Relay Implementation**:
- Peer registration: Any peer can register (public relay), OR whitelist/API keys (private relay)
- Packet forwarding: Any registered peer can send to any other peer (OR P2P ACLs if implemented)
- Admin access: Separate admin role (SSH access) vs user role (relay client)

### 11.3 Monitoring and Logging (CC7.2)

**Requirement**: Monitor systems and respond to anomalies.

**Evidence Required**:
- Successful and failed login attempts (all systems)
- Changes to user permissions (especially privilege escalations)
- Account creation/deletion (especially admin accounts)
- Comprehensive logging and monitoring infrastructure

**FILE Relay Implementation**:
- **Prometheus metrics**: `relay_registrations_total`, `relay_auth_failures_total`, `relay_packets_forwarded_total`
- **Structured logs**: JSON logs to stdout (collected by Loki/Elasticsearch)
- **Alerts**: PagerDuty/Slack for critical events (auth failure spike, relay down)
- **Admin SSH logs**: Centralized via syslog (who SSHed, when, what commands)

### 11.4 Audit Evidence (SOC 2 Type II)

**SOC 2 Type I**: Controls are designed appropriately (point-in-time).

**SOC 2 Type II**: Controls operate effectively over time (3-12 months).

**Evidence for Type II**:
- Continuous logging (prove logs exist for entire audit period)
- Access review reports (quarterly reviews of SSH access)
- Incident response logs (how did you respond to auth failures?)

**FILE Relay Recommendation**:
- **Retain logs for 90 days** (audit period + buffer)
- **Automate access reviews** (script to list SSH users, run quarterly)
- **Document incident response** (playbook for DDoS, compromise, outage)

### 11.5 FILE Relay SOC 2 Readiness

**Current State** (based on ACCESS-CONTROL.md):
- ✅ Prometheus metrics (monitoring foundation)
- ✅ Structured logging design (not yet implemented)
- ✅ CAPoW + rate limiting (DoS prevention)
- ❌ No authentication on metrics endpoint (CC6.1 violation)
- ❌ No admin access controls documented (CC6.3 gap)
- ❌ No audit logging for admin actions (CC7.2 gap)

**Remediation for SOC 2**:
1. **Secure metrics endpoint**: Implement HTTP Basic Auth or network isolation (ACCESS-CONTROL.md Level 1)
2. **Document admin access**: Create ADMIN-ACCESS.md with SSH key management, MFA requirements
3. **Enable SSH audit logging**: Configure syslog forwarding to centralized log server
4. **Create incident response playbook**: INCIDENT-RESPONSE.md with DDoS, breach, outage procedures

## 12. Synthesis and Recommendations

### 12.1 Architectural Validation

**FILE's 5-Level ACL Design is Sound**:

| Level | FILE's Approach | Industry Analog | Verdict |
|-------|----------------|----------------|---------|
| **Level 1: Admin ACLs** | Network isolation or HTTP Basic Auth | Standard practice (Prometheus, Grafana) | ✅ Correct |
| **Level 2: Network ACLs** | Open to 0.0.0.0/0 + CAPoW | TURN servers, Tailscale DERP | ✅ Correct |
| **Level 3: Registration ACLs** | CAPoW-only (public), API keys (managed) | Coturn REST API, Tailscale keys | ✅ Correct |
| **Level 4: P2P ACLs** | Client-side filtering (relay doesn't enforce) | LibP2P, Signal | ✅ Correct |
| **Level 5: Application ACLs** | Client responsibility | Universal (no relay enforces app logic) | ✅ Correct |

**Key Insight**: FILE's "dumb pipe" relay philosophy aligns with industry best practices (Tailscale, Signal, LibP2P). Relays should authenticate peers but not enforce application-level policies.

### 12.4 Security Trade-offs

| Decision | Pros | Cons | Recommendation |
|----------|------|------|----------------|
| **CAPoW-only (no API keys)** | Simple, scalable, privacy-preserving | Cannot ban users, no quotas | ✅ **Use for public relay** |
| **API keys + quotas** | User management, billing, abuse control | Requires database/cache, privacy concerns | ✅ **Use for managed relay** |
| **P2P ACLs (relay-enforced)** | Stops spam at relay, saves bandwidth | Relay learns social graph, adds latency | ⚠️ **Only if spam is proven problem** |
| **OAuth 2.0** | Industry standard, fine-grained scopes | Complex, requires auth server | ❌ **Overkill—use HMAC tokens** |
| **Full IP logging** | Easy debugging, incident response | GDPR violation, privacy risk | ❌ **Never—always hash IPs** |
| **No authentication** | Zero friction, maximum privacy | DoS trivial, abuse rampant | ❌ **Never—at minimum use CAPoW** |
